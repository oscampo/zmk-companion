# ZMK Companion v1.0.6

> **The installer below only updates the Windows app.** This release
> also changes the keyboard's firmware (`firmware/` in this repo), which
> does not take effect until you rebuild and reflash your `zmk-config`.
> Installing `ZmkCompanion-Setup-1.0.6.exe` alone does **not** apply it.
> That firmware change is **not confirmed to fix** the random page
> flashing some users see, see Highlights and Known limitations below
> before you spend time reflashing expecting that to be resolved.

## Highlights

- **Fixed: sports tokens (`{sports.next_game:...}`, `{sports.live:...}`,
  `{sports.last_game:...}`) could go completely silent.** As of the 2026
  NFL preseason opener, ESPN's site API started rejecting every request
  from the app with a 403, with no trace in the log (the error was
  swallowed silently). Root cause confirmed against the live API: the
  block happens at HTTP/2 protocol negotiation, not on request headers,
  `curl` (which only ever offers HTTP/1.1) got through fine, no amount
  of browser-shaped headers on the HTTP/2 side did. The app now pins its
  sports requests to HTTP/1.1, and fetch failures are logged instead of
  disappearing, so a future block like this won't be invisible again.
- **Fixed: `{sports.last_game:...}` could still show nothing early in a
  new season.** v1.0.5's fix only covered the off-season gap (before any
  game in the new season had been played at all). A team on a bye in the
  first week or two of an *already-started* season hit the same empty
  result, the walk simply ran out of steps without ever falling back to
  the prior season. The fallback now triggers whenever the season's own
  calendar is exhausted, not just when it never had anything to check.
- **Changed (firmware): the BLE low-latency connection request is now
  retried instead of sent once.** on_connected() asked the host for a
  low-latency connection a single time and never verified it landed; on
  the link to the PC that request was seen going completely unanswered
  for an entire session, no error, no retry. It's now retried until
  confirmed. **This has NOT been confirmed to fix the random page
  flashing/erratic rendering some users see after certain reconnects**,
  a real-world test after this change still showed the same behavior.
  The only workaround confirmed to work so far is power-cycling both
  halves of the keyboard. See Known limitations below. **Requires
  reflashing the firmware** (`firmware/` in this repo, pulled in as a
  west module) to take effect, the Windows installer alone doesn't
  update the keyboard side.
- **Improved: the display page cycle stops spinning uselessly during a
  long disconnection.** If the keyboard is out of range for more than 5
  minutes (left at home, PC asleep, etc.), the app no longer keeps
  advancing pages in the background with nothing to show for it. It
  resumes normally as soon as the keyboard reconnects.

## Requirements

- Windows 10, build 19041 or later
- [.NET 8 Desktop Runtime](https://dotnet.microsoft.com/download/dotnet/8.0)
- A ZMK keyboard with the display GATT service enabled, see
  [`docs/user_guide.md`](https://github.com/oscampo/zmk-companion/blob/main/docs/user_guide.md#firmware)
  for what that requires. Not supported on stock ZMK firmware.

## Install

Download `ZmkCompanion-Setup-1.0.6.exe` below and run it, no admin rights
needed. The installer isn't code-signed, so Windows SmartScreen will flag
it as an unrecognized publisher on first run, that's expected for an
indie/open-source tool without a paid certificate, not a sign of anything
malicious, click "More info" → "Run anyway" to proceed. Full walkthrough in
[`docs/user_guide.md`](https://github.com/oscampo/zmk-companion/blob/main/docs/user_guide.md).

To get the firmware fix above, rebuild and reflash from your `zmk-config`
(west pulls in this repo's `firmware/` automatically, see
[`zmk-companion-template`](https://github.com/oscampo/zmk-companion-template)
for the reference setup), the installer only updates the Windows app.

## Known limitations

- **Random page flashing / erratic rendering after reconnecting is still
  unresolved.** The BLE retry change above was a reasonable suspect
  (the low-latency request going unanswered matches the timing of the
  reported delays) but a real-world test after applying it showed the
  same erratic behavior, so it isn't the (or isn't the whole) fix. The
  only workaround confirmed to work consistently so far is power-cycling
  **both halves** of the keyboard. A separate, narrower symptom, brief
  blank/stale page flashes for the first 1-2 minutes right after a
  reconnect specifically, was traced to Windows' own BLE stack
  throughput settling after a resume/unlock (a plain differential write
  measured at 2390ms right after reconnect vs. 3-60ms normally), that
  part is outside what this app or the firmware controls.
- If ESPN tightens its API blocking again (a WAF change on their side,
  not something under this project's control), sports tokens could go
  silent again, this time the failure will at least be visible in the
  debug log.
- The display firmware is currently written for one reference keyboard
  (eyelash_corne). It should work on any ZMK board using a `nice_view`
  display, but that hasn't been verified on hardware other than the
  reference board yet, see
  [zmk-companion-template](https://github.com/oscampo/zmk-companion-template)
  if you'd like to try it and report back.
- Auto-start scripts are only reliably portable (export/import, and the
  shipped demo script) when they live in
  `%LOCALAPPDATA%\ZmkCompanion\scripts\`, a command referencing a script
  elsewhere on disk can't be detected and bundled automatically.
- `clients/cli` and `clients/ios` (older Python scripts) only speak the
  legacy plain-text display characteristic, not this app's current
  cell-grid/bitmap protocol.
